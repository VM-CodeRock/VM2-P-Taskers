Design Philosophy

Core Principle
Agents are specialists, not generalists. The Orchestrator coordinates — humans decide. Quality over speed at bid decisions; speed over quality at monitoring. Every agent has a defined confidence floor below which it escalates rather than acts.
PrincipleApplication
Specialist agentsOne agent, one function, one clear quality standard
Orchestrator routes, humans decideNo strategic decision is made autonomously — ever
Human gates are binaryGo/No-Go at gates — not editorial review sessions
Confidence floorsBelow floor → escalate with specific question, not a weak output
Audit trail firstEvery action logged immutably — protest defense + CMMC compliance
Schema disciplineAll inter-agent data in versioned, validated schemas — never free text

AUTONOMOUS · NO HUMAN TRIGGER

Key Rule
Gates are binary (Go/No-Go), not editorial. You make a strategic call — you don't wordsmith agent output at gates. Gates surface as Teams Adaptive Cards, not emails or dashboards you have to remember to check.

Entra ID: Agent Identity

  • Every agent has a Managed Identity — no shared credentials, no passwords to rotate
  • Managed Identities assigned to Entra ID security groups with role-based access (BD-Agents, Proposal-Agents groups)
  • Conditional Access policies: agents can only call internal APIs from within the Azure environment — no exfiltration path
  • Compromised agent? Revoke its Managed Identity — one action, contained blast radius

Teams: Human Gate Interface

Design Rule
Every human-in-the-loop gate surfaces as an Adaptive Card in Teams — not an email, not a dashboard. You tap Approve / No-Bid / Needs More Info directly in Teams. Power Automate is the plumbing that fires the card and routes your response back to the Orchestrator.

The Transfer Mechanism
Every agent reads from a config.json file. Personal environment uses Dropbox + Todoist + Railway. Enterprise swaps to SharePoint + Teams + Azure. The agent logic never changes — only the config. This is the entire transfer mechanism.

Trust Framework

Dimension 1: Trust From You (Agent Reliability)

  • Confidence scoring: Every output declares confidence (0.0–1.0); below floor → escalate with a specific question, not a weak output
  • Explainability by default: Every output includes a structured rationale — what sources used, why that conclusion; not optional narrative
  • Shadow mode before live: 5–10 shadow runs before any agent touches real work

Dimension 2: Trust From Your Team

  • Transparency: Agents never pretend to be human — every output labeled with agent name, model, confidence score
  • Graduated autonomy: Draft → 100% review → spot-check → exception-only; team controls their own autonomy settings per agent
  • Feedback loop: Accepted / Accepted with edits / Rejected rating on every output; deltas feed prompt improvement

Dimension 3: Trust From the Enterprise

  • Agent Constitution: Plain English governing document — what every agent can and cannot do; reviewed by every new agent before deployment
  • Immutable audit trail: timestamp, agent ID, model, input hash, output hash, confidence, gate result — cannot be deleted or modified
  • Kill switch: Individual agent, function cluster, or full system — visible in Teams dashboard to all team members

Verification Record Schema

Permanent Attachment
Every verifier produces a verification_record that travels with the output permanently: verification_id, agent_verified, timestamp, compliance_check result, quality_score (0–10), quality_issues list, adversarial_findings list, recommendation (approve / revise / reject), model_used, human_reviewed flag. This record is stored alongside every piece of agent output — forever. It is the foundation of the Lessons Learned system.

Calibration Agent (Meta-Layer)

Sits above the Lessons Learned Agent. Periodically validates: are verifier scores actually predictive of outcomes we consider good? If Quality Verifier scores 8.5 but humans are still making significant edits, the rubric is wrong. Detects this by correlating verifier scores with human edit rates and win/loss outcomes.

The Compounding Loop
Agent produces output → Verifier evaluates → Verification record stored → Human gate decision + edits captured → Outcome data linked → Lessons Learned Agent aggregates weekly → Prompt Improvement Report → You review → GitHub merge → Updated prompts loaded by agents → Improvement reflected in next verification cycle. The loop closes. The system learns from itself.

The Risk You Cannot Engineer Away
Judgment substitution — the slow, invisible process by which your organization stops exercising strategic judgment because agents always have a confident answer. The best agent frameworks make humans more capable. The worst make them dependent. This risk lives with leadership, not with the architecture.

Pre-Build Checklist — 12 Architectural Decisions

Critical Gate
These 12 decisions must be made before a PRD is written. The PRD formalizes decisions already made — it is not the place where decisions happen.
  • Orchestration Pattern Hierarchical vs. event-driven vs. hybrid (recommended: event-driven for Intelligence Layer, hierarchical for Capture/Proposal). Most consequential technical decision. Everything else derives from it.
  • Agent Granularity Boundaries Define agent boundaries on a whiteboard before any prompts are written. Boundaries are far cheaper to move at this stage than after build. Each agent: one function, one input, one output, one quality standard.
  • State Machine Design Every pursuit state, every valid transition, every invalid transition, and what happens when RFPs change mid-pursuit. Cosmos DB schema, SharePoint structure, Teams cards, and routing logic all derive from this.
  • Idempotency Design Every agent action must produce identical results when run twice. Unique run ID derived from inputs; check before executing. Without this: duplicate proposal sections, duplicate tasks, duplicate files.
  • Context Window Management Strategy Hierarchical summarization, context budget allocation per agent, working memory vs. long-term memory distinction. Design for chunked processing from day one — do not wait until you hit limits.
  • Amendment & Change Handling GovCon-specific: RFPs change. Needs amendment detection agent, impact assessment, selective agent re-run capability, version comparison in SharePoint. Not an edge case — a first-class event.
  • Multi-Tenancy Decision If Changeis grows or white-labels this framework, tenant isolation must be designed in from day one. If not needed, the decision must be explicit — not assumed.
  • Failure Mode Taxonomy Degraded / Blocked / Corrupting / Silent / Catastrophic. Each class needs detection method, response procedure, and recovery path. Especially: what does the team do when the Orchestrator fails during an active proposal with a 48-hour deadline?
  • Testing Architecture Unit (per-agent benchmark inputs/outputs), integration (full workflow on synthetic RFP), regression (every incident generates a permanent test case), shadow mode as continuous production monitoring. Define testing gates before writing agent code.
  • Observability Architecture Logs (structured, per-action), Metrics (aggregated signals), Traces (end-to-end per pursuit). Choose stack before building first agent — Azure Monitor + Power BI. Instrument from agent one.
  • Interface Contract Registry Every agent pair needs: exact input/output schema, error response format, timeout behavior, versioning strategy. Define in GitHub schema registry before build. Agents are built to the contract — not the other way around.
  • Bootstrapping Strategy Lessons Learned Agent needs historical data; Quality Verifier needs calibration data; confidence floors need observations. Seed from VM2 run history and manual proposal archives before go-live. Start with conservative floors and adjust up.
