1. System Overview

VM2 is a fully automated AI task pipeline built on Perplexity Computer. It receives work instructions via email, direct chat, or Todoist, executes them through AI agents, publishes HTML deliverables to a password-protected Railway web portal, and backs up everything to Dropbox and GitHub automatically. As of July 26, 2026, the repo contains 1,189 deliverables (git-verified via git ls-tree file count) across 9 active scheduled crons (reduced from 14 on 2026-06-03 per cost optimization directive).

  • State is dual-written to two paths kept in sync:
    • PRIMARY: /home/user/workspace/cron_tracking/gmail_intake/state.json
    • FALLBACK: /home/user/workspace/cron_tracking/6a1f1c3b/state.json
  • Emails with “VM2” in subject/body are parsed as task instructions
  • Each task spawns a dedicated Perplexity Computer session
  • Completed emails are labeled vm2-done and a reply is sent with the deliverable link
  • Thread tag extraction (v4.3): Subject lines containing [thread:slug] are parsed; the slug is injected into the deliverable's data-thread portal attribute and "thread" context slug field automatically
  • Workspace reset resilience (Issue #19, v5.8): State files lost on sandbox reset are rebuilt by querying Gmail API with broad VM2 sweeps plus supplementary historical subject queries. Deliverables on GitHub/Dropbox/Railway are never affected.

2.5.3 Task Close-Out Procedures (v5.9)

One-shot close-out: (1) GET task from Todoist. (2) Add vm2-done label. (3) POST /api/v1/tasks/{id}/close with X-Request-Id (UUID4). (4) Update cron_tracking/todoist_vm2/state.json — NOT recurring_state.json.

Recurring close-out: (1) GET task from Todoist. (2) Append delivery log line to description: YYYY-MM-DD Delivered: {URL}. (3) POST /api/v1/tasks/{id} with X-Request-Id (UUID4). (4) POST /api/v1/tasks/{id}/close with X-Request-Id (UUID4). (5) Append entry to cron_tracking/todoist_vm2/recurring_state.json.

YPO Tracker Rebuild — 2026-06-29: cron_tracking/ypo_tracker/introductions.json was lost in a workspace reset and successfully rebuilt on 6/29 by reading the latest published YPO Weekly Backlog deliverable HTML and re-extracting the introductions/backlog data from its content, rather than relying solely on Dropbox config backups.

General tracker-state rebuild procedure (applicable beyond YPO):

  1. Identify the most recent published deliverable HTML for the tracker in question (e.g., ypo-weekly-backlog-YYYY-MM-DD.html) via portal.html or GitHub repo listing.
  2. Fetch/read that deliverable's full HTML content, including its Session Context JSON block, which typically embeds the underlying structured data.
  3. Re-extract the structured data (e.g., introductions list, backlog items) from the deliverable content.
  4. Write the reconstructed JSON to the expected cron_tracking/{tracker}/ path.
  5. Validate against the next scheduled run of that tracker's cron to confirm no duplicate or missing entries.

This pattern supplements the general Workspace Reset Recovery Playbook and should be used whenever a specific tracker's state file (not just cron_tracking/ as a whole) needs targeted reconstruction.
