08q Task Close-Out Procedures (v3.9)

Formalized 2026-06-27 — One-Shot vs Recurring Close-Out

These two flows are mutually exclusive. Mixing them causes state corruption.

One-Shot Tasks (VM2 label only, no vm2-recurring):

  1. GET task from Todoist REST API: https://api.todoist.com/api/v1/tasks/{id}
  2. Add vm2-done label (ID 2183604438) via PATCH request
  3. POST https://api.todoist.com/api/v1/tasks/{id}/close with X-Request-Id (UUID4)
  4. Update cron_tracking/todoist_vm2/state.json — NOT recurring_state.json

Recurring Tasks (VM2 + vm2-recurring):

  1. GET task from Todoist REST API
  2. Append delivery log line to description: YYYY-MM-DD Delivered: {URL}
  3. POST https://api.todoist.com/api/v1/tasks/{id} with updated description + X-Request-Id (UUID4)
  4. POST https://api.todoist.com/api/v1/tasks/{id}/close with X-Request-Id (UUID4)
  5. Append entry to cron_tracking/todoist_vm2/recurring_state.json

⚠ Issue #20 — FAA Delivery-Log Discipline Gap (NEW v3.9)

08t Cron Scheduling Infrastructure Failure Recovery — Issue #24 (recurred 7/19–7/22)

⚠ Issue #24 — Cron Scheduling Infrastructure Transients (observed 7/16–7/17, recurred 7/19–7/22)

Multiple scheduled cron runs failed to start during 7/16–7/17 with a platform-level "internal error while starting" failure. This is distinct from Issue #23 (Todoist DNS resolution failures at the REST-API-call level) — Issue #24 occurs before any task logic executes, at the scheduling/dispatch layer itself. The same transient recurred 7/19–7/22, confirming this is an ongoing (not one-time) platform characteristic to monitor for, not a resolved incident.

Detection:

  1. Compare each cron's cron_tracking/{id}/state.json last_run timestamp against its expected schedule interval. A gap exceeding roughly 2x the expected interval, with no corresponding entry in the deliverable log or portal, is the primary indicator.
  2. Cross-reference against the platform's own run history for the cron ID, if available, looking for entries explicitly marked as failed-to-start rather than failed-during-execution.

Recovery procedure:

  1. Do NOT attempt to manually re-trigger a missed run mid-window — the failures observed 7/16–7/17 were self-clearing on the next regularly scheduled invocation, with no cron definitions lost.
  2. Verify the cron definition itself is intact (schedule, prompt, step budget) via schedule_cron(action="list") or the tracked cron table at §06 — a scheduling infrastructure transient does not corrupt the cron definition.
  3. If a run is confirmed skipped (not merely delayed), note the gap in that cron's next successful run's summary/changelog so downstream reconciliation (e.g., deliverable counts, weekly digests) accounts for the missed cycle rather than silently under-counting.
  4. If failures persist beyond 2 consecutive expected intervals for the same cron, escalate for manual review rather than continuing to wait for self-clearing.
  5. This issue requires no data recovery action (no state or deliverable loss observed) — it is purely a monitoring and reconciliation concern.
