1. System Overview

VM2 is a fully automated AI task pipeline built on Perplexity Computer. It receives work instructions via email, direct chat, or Todoist, executes them through AI agents, publishes HTML deliverables to a password-protected Railway web portal, and backs up everything to Dropbox and GitHub automatically. As of July 12, 2026, the repo contains 1,189 deliverables across 9 active scheduled crons (reduced from 14 on 2026-06-03 per cost optimization directive).

15b. Portal Schema Drift Recovery — Issue #21 (NEW v6.0)

Issue #21 — Portal Schema Drift (identified 7/4): portal.html thead declares 6 columns (Created, Title, Type, Project, Updated, Link) but tbody rows contain only 5 <td> cells. This mismatch predates this run and root cause is under investigation. The Weekly Digest cron (972eaa3f) is blocked until reconciled, since its rendering logic depends on consistent column counts.

Interim guidance (until reconciliation):

  1. Do NOT attempt to fix the header/row mismatch as part of routine deliverable publishing — this is reserved for the Weekly Digest reconciliation effort.
  2. New rows added to portal.html must match the dominant existing 5-td row pattern already used by the majority of rows in the table, not the 6-column header.
  3. Never touch or modify index.html as part of any schema fix.
  4. When the Weekly Digest reconciliation eventually runs, it should: (a) inventory all row variants in tbody, (b) determine the single dominant schema, (c) either normalize the header to match the dominant row schema or normalize all rows to match the header — whichever requires fewer destructive edits, (d) re-run Weekly Digest generation once schema is consistent.

15c. Tracker State Rebuild Pattern — YPO Tracker (NEW v6.0)

YPO Tracker Rebuild — 2026-06-29: cron_tracking/ypo_tracker/introductions.json was lost in a workspace reset and successfully rebuilt on 6/29 by reading the latest published YPO Weekly Backlog deliverable HTML and re-extracting the introductions/backlog data from its content, rather than relying solely on Dropbox config backups.

General tracker-state rebuild procedure (applicable beyond YPO):

  1. Identify the most recent published deliverable HTML for the tracker in question (e.g., ypo-weekly-backlog-YYYY-MM-DD.html) via portal.html or GitHub repo listing.
  2. Fetch/read that deliverable's full HTML content, including its Session Context JSON block, which typically embeds the underlying structured data.
  3. Re-extract the structured data (e.g., introductions list, backlog items) from the deliverable content.
  4. Write the reconstructed JSON to the expected cron_tracking/{tracker}/ path.
  5. Validate against the next scheduled run of that tracker's cron to confirm no duplicate or missing entries.
